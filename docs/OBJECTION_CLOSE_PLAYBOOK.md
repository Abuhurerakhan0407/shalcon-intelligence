# Shalcon Intelligence — Objection + Close Playbook

Purpose: handle risk questions without inventing certainty, then move qualified prospects to one clear next step.

## Operating rule
An objection is information, not something to overpower. Answer the concern, verify whether it is resolved, and either advance, narrow the scope, or disqualify.

Never use fake scarcity, invented client results, guaranteed revenue, or made-up technical certainty to close a deal.

## 1. “We already have WhatsApp / a chatbot.”
Response logic:
- Confirm what the existing tool actually does.
- Separate the channel/interface from the operating workflow behind it.
- Map missing steps: qualification, booking/routing, follow-up, CRM write-back, escalation, reporting.

Close question:
“Would it be useful to map what happens before and after the current WhatsApp/chatbot step?”

## 2. “AI makes mistakes.”
Response logic:
- Agree that uncontrolled automation can fail.
- Explain approved-response boundaries, validation, confidence thresholds, deterministic rules where needed, and human escalation.
- Scope the pilot around tasks where errors can be tested and contained.

Close question:
“Which requests would you never allow the system to handle without staff review?”

## 3. “Can you guarantee revenue / more bookings?”
Response logic:
- Do not guarantee customer behavior.
- Commit only to written deliverables, acceptance criteria and agreed support obligations.
- Define operational indicators that can be measured before and after launch.

Close question:
“If we measure response, completion, routing and booking workflow performance first, is that enough to judge whether the pilot deserves expansion?”

## 4. “Why not just use ChatGPT ourselves?”
Response logic:
A model can generate text. A production system also needs:
- approved data access;
- workflow state;
- permissions;
- integrations;
- routing;
- error handling;
- retries/fallbacks;
- logging;
- monitoring;
- human ownership;
- maintenance.

Close question:
“Do you want a chat interface, or do you want the inquiry to reliably reach the right business outcome and system of record?”

## 5. “This is expensive.”
Response logic:
- Do not immediately discount.
- Recheck whether the proposed scope is larger than the validated pain.
- Separate implementation, recurring support and third-party usage costs.
- Offer a bounded pilot when the wider system is not yet economically justified.

Close question:
“Should we reduce this to the one workflow that can prove whether the economics make sense?”

## 6. “Can you do it cheaper?”
Before changing price, change one of:
- scope;
- channels;
- integrations;
- reporting depth;
- support level;
- implementation sequence.

Do not silently keep the same obligations at a lower price.

Use:
“We can reduce the commercial size by reducing scope. I don’t want to quote the same system cheaper and then under-deliver.”

## 7. “How fast can you launch?”
Response logic:
- Never quote an exact go-live before integrations/access are known.
- Explain stages: workflow confirmation → prototype → integration → UAT → production stabilization.
- Identify client dependencies that control timing.

Close question:
“If access and approvals are ready, we can produce a realistic implementation plan after the audit. Who owns those approvals on your side?”

## 8. “What if Meta / the AI provider / CRM goes down?”
Response logic:
- Third-party uptime is not controlled by Shalcon.
- Design explicit failure states: retry, queue, alert, human fallback, manual override.
- Define what the business should do during outage conditions.

Close question:
“Which failure should trigger an immediate staff handoff versus a retry?”

## 9. “What about privacy / sensitive data?”
Response logic:
- Minimize collected data.
- Identify data categories before implementation.
- Use least-privilege access.
- Keep public demos synthetic.
- Avoid placing unnecessary sensitive content in analytics/logs.
- Put client-specific processing/security obligations into the written agreement when required.

Close question:
“What sensitive fields does this workflow genuinely need, and which can we exclude entirely?”

## 10. “We need to think about it.”
Do not chase with pressure.
Ask what remains unresolved:
- economics;
- trust;
- timing;
- stakeholder approval;
- technical feasibility;
- competing priority.

Then agree one next action and date, or move to nurture.

## 11. “Send a proposal.”
A proposal request is not automatically qualified.
Before sending, confirm:
- workflow;
- decision maker;
- integrations;
- approximate volume;
- acceptance criteria;
- timeline signal;
- commercial scope;
- client dependencies.

If these are unknown, send an audit summary rather than a fictional proposal.

## 12. Close paths

### Path A — Pilot
Use when one workflow is clear and measurable.
Next step: send bounded SOW with implementation fee, dependencies, UAT criteria and measurement plan.

### Path B — System proposal
Use when multiple connected workflows are clear and the decision maker is engaged.
Next step: technical confirmation if needed, then full proposal/SOW.

### Path C — Technical validation
Use when the business case is real but an API/integration/access assumption could materially change scope.
Next step: validate that dependency before commercial commitment.

### Path D — Nurture
Use when timing/budget is not ready but fit exists.
Next step: record a specific revisit date and useful asset to send.

### Path E — Disqualify
Use when economics, safety, authorization or expectations do not make sense.
Do not keep an opportunity open for vanity pipeline.

## 13. Discount guardrail
Any discount must be tied to a documented trade-off or commercial reason such as:
- reduced scope;
- longer commitment with clear termination terms;
- reference/case-study permission only after verified delivery and separate approval;
- changed payment schedule;
- strategic pilot approved by the owner.

Never exchange discount for an unverified testimonial or predetermined positive result.

## 14. Pre-close checklist
- Decision maker identified.
- Scope understood.
- Client dependencies listed.
- Third-party costs separated.
- Acceptance criteria testable.
- Human escalation defined.
- Sensitive data constraints known.
- Timeline assumptions written.
- No unsupported outcome promise made.
- Next step has an owner and date.
